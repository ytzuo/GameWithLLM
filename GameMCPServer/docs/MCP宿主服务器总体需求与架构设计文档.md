# MCP宿主服务器总体需求与架构设计文档

## 1. 文档定位

本文档用于确定 MCP宿主服务器在系统中的总体定位、核心需求、能力边界和架构设计。

本阶段不深入展开具体接口协议、字段结构、工具参数 Schema 和详细异常码，重点先明确：

```text
1. MCP宿主服务器是什么
2. MCP宿主服务器负责什么
3. MCP宿主服务器不负责什么
4. MCP宿主服务器和 Unity、大模型、MCP客户端线程之间如何协作
5. 在独立进程部署方案下，整体系统架构如何设计
```

------

# 2. 系统背景

在基于大模型驱动 NPC 的 Unity 游戏系统中，用户可以向某个 NPC 提问，远程大模型负责理解用户意图，并决定是否需要调用工具来查询游戏状态或控制 NPC 行为。

例如：

```text
用户：你能走到门口吗？
大模型：判断需要调用 move_to 工具
Unity：控制对应 NPC 移动到门口
大模型：根据移动结果生成回复
NPC：展示回复给用户
```

为了让大模型能够安全、规范地调用 Unity 中的 NPC 行为，需要在 MCP客户端线程和 Unity 游戏客户端之间引入一个独立的 MCP宿主服务器。

该服务器作为独立进程运行，专门负责 MCP 工具声明、工具调用接收、NPC 身份绑定、Unity 命令转发和执行结果返回。

------

# 3. MCP宿主服务器的系统定位

在方案中，MCP宿主服务器作为一个独立进程存在。

它位于：

```text
MCP客户端线程 与 Unity游戏客户端 之间
```

其核心定位是：

```text
MCP宿主服务器是一个独立的工具宿主服务和 Unity 行为转发网关。
```

它对 MCP客户端线程提供标准化工具能力，对 Unity 游戏客户端提供命令转发能力。

也就是说，它既不是大模型客户端，也不是 Unity 游戏逻辑本身，而是中间的工具服务层。

可以简单理解为：

```text
大模型负责“决定要做什么”
MCP客户端线程负责“和大模型对话”
MCP宿主服务器负责“把工具调用转发给 Unity”
Unity游戏客户端负责“真正执行 NPC 行为”
```

------

# 4. 总体需求

## 4.1 工具声明需求

MCP宿主服务器需要能够向 MCP客户端线程声明当前可用的 MCP tools。

这些 tools 代表大模型可以调用的游戏能力，例如：

```text
查询 NPC 状态
查询 NPC 位置
控制 NPC 移动
让 NPC 说话
让 NPC 播放动画
查询附近对象
与游戏对象交互
```

工具声明需要满足以下要求：

```text
1. 只暴露经过注册和允许的大模型工具
2. 工具名称、用途和参数格式需要明确
3. 工具名与 Unity 中方法名严格对应，不需要命令转换
```

工具声明的作用是限制大模型的可操作范围。

大模型只能调用 MCP宿主服务器声明过的工具，而不能随意调用 Unity 内部 API 或任意游戏命令。

------

## 4.2 工具调用接收需求

当大模型返回 tool_calls 后，MCP客户端线程会调用 MCP宿主服务器提供的对应工具。

MCP宿主服务器需要接收来自 MCP客户端线程的工具调用请求。

工具调用请求中通常需要包含：

```text
工具名称
工具参数
当前会话信息
当前 NPC 上下文
请求标识
```

MCP宿主服务器接收到调用后，需要判断：

```text
1. 这个工具是否存在
2. 参数是否合法
3. 当前 NPC 是否存在
4. 当前 NPC 是否允许执行该行为
5. 是否可以转发给 Unity 执行
```

------

## 4.3 NPC 身份绑定需求

大模型不应该直接管理 NPC ID。

因为大模型只需要理解“当前对话的 NPC 要执行某个行为”，不应该让它直接决定操作哪个 NPC。

因此，MCP宿主服务器需要支持 NPC 身份绑定能力。

也就是：

```text
大模型调用：move_to(x, y, z)

系统内部转换为：
让 npc_001 执行 move_to(x, y, z)
```

NPC 身份可以由 MCP客户端线程传入，也可以由 MCP宿主服务器根据会话上下文映射得到。

设计原则是：

```text
大模型侧不直接感知 npc_id
系统内部负责绑定 npc_id
Unity 侧根据 npc_id 执行具体行为
```

这样可以避免大模型错误操作其他 NPC，也方便系统做权限控制和安全限制。

------

## 4.4 Unity 命令转发需求

MCP宿主服务器直接将 MCP 工具调用转发给 Unity 游戏客户端，工具名与 Unity 中方法名严格对应，不需要额外的命令转换。

例如：

```text
MCP 工具：move_to
Unity 方法：move_to

MCP 工具：say
Unity 方法：say

MCP 工具：get_npc_status
Unity 方法：get_npc_status
```


MCP宿主服务器需要保证：

```text
1. 工具名与 Unity 方法名严格一致
2. 工具参数直接透传给 Unity
3. 每个命令需要附带 npc_id
4. 每个命令需要可以追踪执行结果

```

------

## 4.5 Unity 通信需求

在独立进程方案下，MCP宿主服务器需要通过网络通信方式与 Unity 游戏客户端交互。

推荐通信方式：

```text
WebSocket 或 TCP
```

原因是：

```text
1. 需要双向通信
2. Unity 需要持续接收命令
3. MCP宿主服务器需要等待 Unity 返回执行结果
4. 后续可能支持多个 Unity 客户端连接
5. 行为命令和执行结果具有明显的请求-响应关系
```

通信关系为：

```text
MCP宿主服务器  →  Unity游戏客户端
发送 NPC 行为命令

Unity游戏客户端  →  MCP宿主服务器
返回命令执行结果
```

Unity 游戏客户端收到命令后，不应该直接在网络线程中操作 Unity 对象，而应该将命令投递到 Unity 主线程任务队列中，由 Unity 主线程执行。

------

## 4.6 执行结果返回需求

Unity 执行完命令后，需要将结果返回给 MCP宿主服务器。

MCP宿主服务器再将 Unity 返回结果包装为 MCP 工具调用结果，返回给 MCP客户端线程。

MCP客户端线程拿到工具结果后，再把结果提交给远程大模型，由大模型生成最终自然语言回复。

因此，MCP宿主服务器需要具备：

```text
1. 接收 Unity 执行结果的能力
2. 根据请求标识匹配对应工具调用的能力
3. 将 Unity 结果转换为 MCP 工具结果的能力
4. 将失败信息、超时信息、执行状态返回给 MCP客户端线程的能力
```

------

## 4.7 多 NPC 并发需求

系统可能同时存在多个 NPC 与用户交互。

因此，MCP宿主服务器需要支持多个 NPC 的工具调用并发处理。

例如：

```text
npc_001 正在移动
npc_002 正在说话
npc_003 正在查询附近对象
```

MCP宿主服务器需要保证：

```text
1. 不同 NPC 的请求相互隔离
2. 每个请求都有唯一标识
3. Unity 返回结果能正确匹配到原请求
4. 一个 NPC 的失败不影响其他 NPC
5. 同一 NPC 的冲突行为需要有控制策略
```

初期可以采用较简单的策略：

```text
查询类工具可以并发
行为类工具同一 NPC 同一时间只允许执行一个
```

------

## 4.8 异常处理需求

MCP宿主服务器作为独立服务，需要具备基本的异常处理能力。

需要处理的异常包括：

```text
工具不存在
参数不合法
NPC 不存在
NPC 当前状态不允许执行行为
Unity 客户端未连接
Unity 执行失败
Unity 返回超时
网络连接断开
```

------

# 5. 能力边界

## 5.1 MCP宿主服务器负责的能力

MCP宿主服务器负责以下能力：

```text
1. MCP tools 的注册与声明
2. 接收 MCP客户端线程的工具调用
3. 校验工具名称和参数
4. 绑定 NPC 身份
5. 将 MCP 工具调用转发给 Unity
6. 通过 WebSocket/TCP 与 Unity 游戏客户端通信
7. 向 Unity 发送 NPC 行为命令
8. 接收 Unity 执行结果
9. 将 Unity 结果包装为 MCP 工具调用结果
10. 处理超时、连接断开、执行失败等异常
```

它的核心价值是：

```text
把大模型产生的 tool_call 安全、可控、可追踪地映射成 Unity 中指定 NPC 的实际行为。
```

------

## 5.2 MCP宿主服务器不负责的能力

MCP宿主服务器不负责以下能力：

```text
1. 不负责直接调用远程大模型
2. 不负责管理大模型上下文
3. 不负责维护 NPC 和大模型的一对一会话
4. 不负责生成最终自然语言回复
5. 不负责 Unity 中具体寻路、动画、碰撞、状态机等游戏逻辑
6. 不负责直接操作 Unity 场景对象
7. 不负责玩家输入采集和 UI 展示
8. 不负责复杂 NPC 智能决策
9. 不负责长期记忆和角色人格系统
```

这些能力应由其他模块负责。

------

# 6. 与其他模块的关系

## 6.1 与远程大模型的关系

远程大模型负责：

```text
理解用户输入
判断是否需要调用工具
返回 tool_calls
根据工具执行结果生成最终回复
```

MCP宿主服务器不直接调用远程大模型。

在本架构中，远程大模型只与 MCP客户端线程直接交互。

------

## 6.2 与 MCP客户端线程的关系

MCP客户端线程是 MCP宿主服务器的直接调用方。

MCP客户端线程负责：

```text
管理 NPC 与大模型的一对一会话
向远程大模型发送用户输入
接收远程大模型返回的 tool_calls
调用 MCP宿主服务器中的工具
将工具结果返回给远程大模型
接收大模型最终回复
```

MCP宿主服务器对 MCP客户端线程提供工具服务。

二者关系可以理解为：

```text
MCP客户端线程：负责大模型会话流程
MCP宿主服务器：负责工具调用执行流程
```

------

## 6.3 与 Unity 游戏客户端的关系

Unity 游戏客户端是 MCP宿主服务器的命令执行方。

Unity 游戏客户端负责：

```text
连接 MCP宿主服务器
接收 NPC 行为命令
将命令投递到 Unity 主线程
执行 NPC 具体行为
返回执行结果
```

MCP宿主服务器不直接操作 Unity 对象，只通过协议向 Unity 发送命令。

Unity 侧需要保证：

```text
所有 Unity API 操作都在 Unity 主线程完成
网络线程只负责收发消息
游戏行为逻辑仍然由 Unity 侧系统执行
```

------

# 7. 总体架构设计

## 7.1 独立进程架构

本方案采用 MCP宿主服务器独立进程部署。

整体结构如下：

```text
┌──────────────────────┐
│      远程大模型       │
└──────────▲───────────┘
           │
           │ 大模型请求 / tool_calls / 工具结果
           │
┌──────────▼───────────┐
│    MCP客户端线程      │
│  管理 NPC 会话与模型交互 │
└──────────▲───────────┘
           │
           │ MCP tool 调用
           │
┌──────────▼───────────┐
│    MCP宿主服务器      │
│  工具声明 / 命令转发 │
└──────────▲───────────┘
           │
           │ WebSocket / TCP
           │
┌──────────▼───────────┐
│    Unity游戏客户端    │
│  接收命令 / 主线程执行行为 │
└──────────────────────┘
```

------

## 7.2 逻辑分层

整个系统可以分为四层。

```text
第一层：大模型推理层
第二层：NPC 会话管理层
第三层：MCP 工具宿主层
第四层：Unity 行为执行层
```

对应关系如下：

```text
大模型推理层：
远程大模型负责理解用户意图、生成 tool_calls、生成最终回复。

NPC 会话管理层：
MCP客户端线程负责维护不同 NPC 和大模型之间的会话。

MCP 工具宿主层：
MCP宿主服务器负责工具声明、工具调用、命令转发。

Unity 行为执行层：
Unity游戏客户端负责执行 NPC 具体行为，并返回结果。
```

------

## 7.3 主流程

完整主流程如下：

```text
1. 用户在 Unity 中向某个 NPC 提问。
2. Unity 将用户输入和 NPC 上下文交给 MCP客户端线程。
3. MCP客户端线程根据 npc_id 找到对应的大模型会话。
4. MCP客户端线程向远程大模型发送用户输入。
5. 远程大模型判断需要调用工具，返回 tool_calls。
6. MCP客户端线程调用 MCP宿主服务器中的对应工具。
7. MCP宿主服务器接收工具调用。
8. MCP宿主服务器校验工具和参数。
9. MCP宿主服务器绑定当前 npc_id。
10. MCP宿主服务器将 MCP 工具调用直接转发给 Unity。
11. MCP宿主服务器通过 WebSocket/TCP 将命令发送给 Unity 游戏客户端。
12. Unity 游戏客户端收到命令后投递到 Unity 主线程。
13. Unity 主线程执行 NPC 行为。
14. Unity 游戏客户端将执行结果返回给 MCP宿主服务器。
15. MCP宿主服务器将 Unity 结果转换为 MCP tool result。
16. MCP客户端线程将 tool result 返回给远程大模型。
17. 远程大模型生成最终自然语言回复。
18. MCP客户端线程将回复交给 Unity。
19. Unity 展示 NPC 回复给用户。
```

------

# 8. MCP宿主服务器内部架构

MCP宿主服务器内部建议拆分为以下模块：

```text
MCPHostServer
├── ToolRegistry
├── ToolCallHandler
├── NpcContextBinder
├── UnityCommandAdapter
├── UnityConnectionManager
├── UnityCommandBridge
├── ResultAdapter
├── RequestTracker
└── ErrorHandler
```

------

## 8.1 ToolRegistry

负责管理 MCP tools。

主要职责：

```text
注册工具
维护工具定义
声明工具列表
限制可调用工具范围
维护工具与 Unity 方法名的对应关系
```

------

## 8.2 ToolCallHandler

负责处理 MCP 工具调用。

主要职责：

```text
接收工具调用
查找工具定义
校验工具参数
调用 NPC 绑定模块
调用命令封装模块
调用 Unity 转发模块
返回工具调用结果
```

------

## 8.3 NpcContextBinder

负责绑定 NPC 上下文。

主要职责：

```text
根据会话上下文获取 npc_id
校验 npc_id 是否存在
校验当前请求是否允许控制该 NPC
将 npc_id 注入 Unity 命令
```

------

## 8.4 UnityCommandAdapter

负责将 MCP 工具调用封装为 Unity 可执行的命令。

主要职责：

```text
工具名与 Unity 方法名严格对应，不转换
封装参数结构
补充 npc_id
生成统一的 Unity 命令对象
```

------

## 8.5 UnityConnectionManager

负责维护 MCP宿主服务器与 Unity 游戏客户端之间的连接。

主要职责：

```text
监听 Unity 客户端连接
维护连接状态
处理连接断开
处理重连
支持未来多个 Unity 客户端连接
```

------

## 8.6 UnityCommandBridge

负责向 Unity 发送命令并接收结果。

主要职责：

```text
发送 Unity 命令
接收 Unity 执行结果
根据 commandId 匹配请求
处理命令发送失败
处理 Unity 执行超时
```

------

## 8.7 ResultAdapter

负责转换执行结果。

主要职责：

```text
将 Unity 成功结果转换为 MCP tool result
将 Unity 失败结果转换为 MCP tool error
过滤 Unity 内部不需要暴露的信息
统一返回格式
```

------

## 8.8 RequestTracker

负责追踪正在执行的请求。

主要职责：

```text
记录 requestId 和 commandId 的对应关系
记录请求开始时间
等待 Unity 返回结果
处理超时请求
释放已完成请求资源
```

------

## 8.9 ErrorHandler

负责错误处理。

主要职责：

```text
记录异常原因
输出统一错误信息
```

------

# 9. 方案的架构特点

采用独立进程部署后，MCP宿主服务器具有以下特点。

## 9.1 优点

```text
1. 职责更清晰
2. MCP 工具逻辑和 Unity 游戏逻辑解耦
3. 方便独立开发、测试和调试
4. 方便后续扩展更多工具
5. 方便未来支持多个 Unity 客户端
6. 可以独立监控工具调用状态
7. Unity 崩溃或重启时，MCP 服务可以独立管理连接恢复
```

------

## 9.2 缺点

```text
1. 部署复杂度更高
2. 需要处理网络通信
3. 需要处理 Unity 连接断开和重连
4. 需要设计请求和响应匹配机制
5. 相比进程内调用会有额外通信延迟
```

------

## 9.3 适用场景

独立进程方案适合：

```text
1. NPC 工具能力较多
2. 后续系统需要长期扩展
3. MCP 工具服务希望独立维护
4. Unity 客户端和工具服务需要解耦
5. 未来可能支持多个游戏客户端或多个场景
6. 需要更清晰的监控和调试能力
```

------

# 10. 第一阶段建设目标

第一阶段不追求完整复杂功能，只需要跑通独立进程架构下的最小闭环。

建议第一阶段目标为：

```text
1. MCP宿主服务器可以独立启动
2. Unity 游戏客户端可以连接 MCP宿主服务器
3. MCP宿主服务器可以声明基础 tools
4. MCP客户端线程可以调用 MCP宿主服务器中的工具
5. MCP宿主服务器可以把工具调用转发给 Unity
6. Unity 可以接收命令并在主线程执行
7. Unity 可以返回执行结果
8. MCP宿主服务器可以把结果返回给 MCP客户端线程
```

第一阶段建议只实现少量基础工具：

```text
get_npc_status
get_npc_position
move_to
say
```

这几个工具足够验证：

```text
查询类工具是否能跑通
行为类工具是否能跑通
npc_id 绑定是否正确
Unity 命令转发是否正确
Unity 执行结果是否能返回
```

------

# 11. 总体结论

在方案中，MCP宿主服务器作为独立进程存在，其核心职责是：

```text
作为 MCP 工具宿主服务，声明可调用工具；
作为 Unity 行为转发网关，将工具调用直接转发给 Unity；
作为请求追踪节点，等待 Unity 执行结果并返回给 MCP客户端线程。
```

它的能力边界应保持清晰：

```text
不直接调用大模型
不管理大模型上下文
不执行 Unity 游戏逻辑
不直接操作 Unity 对象
不生成最终 NPC 回复
```

它应该专注于：

```text
工具声明
工具调用
NPC 绑定
命令转发
网络转发
结果返回
异常处理
```

因此，第一版 MCP宿主服务器的设计重点不是复杂智能，而是建立一个稳定、清晰、可扩展的工具调用转发链路。

最终目标是形成如下闭环：

```text
大模型 tool_call
        ↓
MCP客户端线程
        ↓
MCP宿主服务器
        ↓
Unity游戏客户端
        ↓
NPC执行行为
        ↓
Unity返回结果
        ↓
MCP宿主服务器返回 tool result
        ↓
大模型生成最终回复
```
